# Software Architecture and Implementation

## 1. Purpose

This document describes the implementation of the EU AI Act
Legal Information Assistant developed for the accompanying
master's thesis.

It describes the reviewed source-code snapshot, not an
independently certified or production-ready legal system.

## 2. Major Components

### rag_chat.py

Implements the core retrieval functionality.

Main responsibilities:

- Communicating with ChromaDB
- Generating query rewrites and subquestions
- Optional hypothetical-document expansion (HyDE)
- Semantic retrieval
- Candidate reranking
- Preparing the context supplied to the language model
- Communicating with the configured LLM backend
- Caching retrieval-related operations

The reviewed code uses:

    Embeddings: all-MiniLM-L6-v2
    Reranker: ms-marco-MiniLM-L-12-v2
    Collection: research_chunks
    ChromaDB port: 8000
    Maximum context: 8000 characters

The retrieval implementation limits the context supplied to
the generator. Consequently, retrieved evidence may be
incomplete, especially for scenarios requiring many different
legal provisions.

### batch_rag.py

Implements the structured batch-question processing workflow.

Main responsibilities:

- Loading benchmark questions or structured scenarios
- Constructing questions from scenario fields
- Invoking retrieval and language-model generation
- Requesting structured JSON responses
- Parsing generated output
- Applying deterministic risk calibration
- Recording predictions, sources and processing times
- Saving batch results

The current structured prompt requests:

    analysis
    risk_level
    obligations
    articles

It also requests 5–10 obligations and relevant article
numbers supported by the retrieved context.

The implementation contains a per-scenario timeout.

### scenario_batch_rag.py

Provides scenario-specific processing and classification
functions.

It contains:

- Structured scenario-query construction
- Response-extraction helpers
- Keyword and domain heuristics
- Risk inference from scenario metadata
- Deterministic calibration through calibrate_risk_level()

The final predicted risk label may differ from the original
risk label generated by the language model.

This is an important part of the methodology: the reported
end-to-end classification scores belong to the combined
model-and-calibration pipeline.

### scenario_evaluation.py

Compares saved model outputs with the scenario benchmark.

It evaluates:

- Risk-label agreement
- Obligation-count coverage
- Obligation semantic similarity
- Article-set precision, recall and F1
- Citation-format validity
- Processing time and evaluation failures

The evaluator maps results to benchmark scenarios using
scenario IDs.

Evaluation outputs include aggregate_scores and
individual_evaluations.

### analyze_classification.py

Produces class-specific confusion statistics and
precision, recall and F1 values.

Known issue:

The script increments both false positives and false
negatives for a misclassification, then incorrectly sums
FP + FN as the overall incorrect total.

For 56 misclassified scenarios, that summary can therefore
display 112 rather than 56.

The actual number of incorrect scenarios is:

    total evaluated - correctly classified

The class-specific TP, FP and FN definitions are distinct
from this incorrect aggregate calculation.

### server.py

Implements the FastAPI interface for the live chatbot.

Endpoints:

    GET /health
    POST /chat

The live processing path includes:

- User-input handling
- Optional conversation history
- Scenario-field extraction
- Query construction
- Retrieval
- LLM response generation
- Structured parsing
- Risk post-processing
- Response formatting

It shares components with the batch pipeline but includes
additional routing and conversational processing.

Accordingly, the batch benchmark results cannot be applied
directly to the live interface.

### Frontend

The frontend is built with Next.js and TypeScript.

It supports:

- Conversational interaction
- Display of classifications and obligations
- Article and source presentation
- Document attachment controls
- Communication with the FastAPI backend

The frontend also includes a demonstration mode.

If the backend request fails, the reviewed frontend can
produce locally simulated responses.

This fallback is an interface behavior, not evidence that
the retrieval system successfully answered the question.

The current attachment-processing functionality should also
not be interpreted as complete PDF/DOCX content extraction.

## 3. Retrieval Corpus

The repository includes:

    backend/text_chunks.tsv

This file contains processed text chunks used to populate
the retrieval database.

The ChromaDB ingestion script assigns metadata including:

    source
    doc_id
    chunk_index
    length

The expected source identifier is:

    thesis_text_chunks_v1

A consistent text corpus, metadata structure and embedding
configuration are necessary for meaningful reproduction.

The original ChromaDB database does not have to be
distributed if it can be rebuilt from the supplied corpus.

However, rebuilding the database is not automatically
equivalent to reproducing every original retrieval result.

## 4. API Interface

### GET /health

Checks that the FastAPI service is reachable.

It is not a full end-to-end retrieval health check.

### POST /chat

Example request:

    {
      "message": "Analyze an AI recruitment screening system",
      "document_text": null,
      "history": [],
      "fast": false
    }

The response schema includes:

    analysis
    risk_level
    obligations
    articles
    sources
    used_deep_research
    processing_time
    scenario
    mode

The mode field distinguishes classification,
general question answering and clarification behavior.

The live output schema is related to, but not identical
with, the saved batch-experiment schema.

## 5. Configuration

Relevant configuration variables include:

| Variable | Purpose |
|---|---|
| LLM_BACKEND | Selects OpenAI-compatible or Ollama backend |
| OPENAI_API_KEY | OpenAI-compatible API authentication |
| OPENAI_MODEL | Hosted model identifier |
| OPENAI_BASE_URL | Optional alternative API endpoint |
| OLLAMA_MODEL | Local Ollama model identifier |
| CORS_ORIGINS | Allowed frontend origins |
| NEXT_PUBLIC_API_URL | Frontend backend-API address |

Some ChromaDB and retrieval parameters remain constants
inside the Python source files rather than environment
variables.

Changes to configuration may alter runtime behavior.

## 6. Evaluation Methodology

### Risk classification

The benchmark risk label is compared with the final
generated risk label.

    Accuracy = correct classifications / evaluated scenarios

### Obligation-count coverage

The evaluator measures:

    min(generated obligation count /
        benchmark obligation count, 1.0)

This metric does not verify that generated obligations
are legally correct or complete.

### Obligation semantic similarity

Sentence embeddings are used to compare generated and
reference obligations.

Similarity values are automated text-comparison metrics,
not human legal judgments.

### Article identification

Generated article numbers are compared with benchmark
article sets.

The evaluator computes:

    Precision = matching articles / generated articles

    Recall = matching articles / benchmark articles

    F1 = harmonic mean of precision and recall

### Citation validity

The evaluator checks citation formatting using the
expected source-reference pattern.

A correctly formatted citation may still be irrelevant
to the claim it accompanies.

## 7. Reproducing Saved Evaluations

The preserved outputs allow the classification results
to be independently inspected and recalculated.

Example:

    cd backend

    python scenario_evaluation.py \
      scenarios.json \
      ../experiments/V6/scenarios_output_v6.json \
      ../experiments/V6/recomputed_evaluation_v6.json

The same procedure applies to V7.

Use different filenames for regenerated evaluations so
the historical records remain unchanged.

## 8. Historical Reproducibility

The final source files uploaded with the thesis were
compared with the GitHub repository implementation.

They match the reviewed repository snapshot.

However, exact historical generation reproducibility
is subject to limitations:

- Hosted model behavior can change.
- Historical model versions may become unavailable.
- Retrieval results depend on the indexed corpus.
- Local caches and dependency versions may differ.
- The historical V6 source snapshot was overwritten.

The full V6 and V7 outputs and evaluations are preserved,
allowing retrospective analysis without claiming an
identical regeneration environment.

## 9. Known Implementation Limitations

### Retrieval coverage

The retrieval strategy uses bounded context and candidate
selection. Important legal articles can be absent from
the context presented to the generator.

### Calibration

Heuristic post-processing can correct errors but may
introduce other errors when keywords are interpreted
without all relevant legal conditions.

### Structured generation

The system requests structured JSON, but model output
validity is not mathematically guaranteed.

### Live versus batch behavior

The live chatbot includes different preprocessing,
routing and response handling from the benchmark pipeline.

### Frontend demonstration fallback

The interface can display simulated content when the
backend is unavailable.

### Dependency coverage

The optional PDF-chunking script references PyPDF2 and
tiktoken, which are not included in the reviewed
backend requirements file.

These dependencies must be installed separately if that
particular preprocessing script is used.

### Historical report generation

The repository's model-comparison summary generator reads
an outdated JSON key, resulting in null accuracy values.

The accuracy is actually stored at:

    aggregate_scores.risk_classification.accuracy

The summary generator should be corrected before producing
a new consolidated report.

## 10. Security

API credentials must be supplied through secure local
configuration.

No credentials should be included in public source code,
software ZIP files or submitted experiment metadata.

The repository history should be checked for previous
credential exposure. Any confirmed exposed credential
must be revoked or rotated.

## 11. Testing Status

The final V6 and V7 saved predictions and evaluation
records have been checked for consistency.

The current uploaded Python source files match the
reviewed GitHub versions.

Fresh installation, complete backend execution and live
frontend integration have not yet been independently
verified.

This distinction is intentional: inspection of source
and saved results is not the same as successful execution.
